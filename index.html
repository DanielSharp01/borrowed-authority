The browser enforced the server's answer.

The browser automatically asks whether campaigns.banana.com may send a credentialed JSON PATCH. The preflight names the intended method and non-simple header. Auth reflects permission for that origin, so the browser sends the malicious mutation with an admin's cookie. CORS enforced the answer correctly; the server supplied the wrong answer.

Never mutate state in a GET.
GET, HEAD, and POST can be CORS-safelisted methods. A GET with safelisted headers does not need a preflight. The server performs the operation before the browser decides whether the hostile page may expose the response to the hostile script. Safe HTTP methods must stay read-only. Here the two hosts are also same-site, so a SameSite cookie may still accompany the cross-origin request. Sources: https://fetch.spec.whatwg.org/ and https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html

HTML forms can submit cross-origin GET and POST requests using form-urlencoded, multipart, or plain-text bodies. Those shapes are deliberately compatible with the old web and do not preflight. The cookie identifies the session. The token shows the requester could read protected application state.

The first click establishes the browser and server, then requests a token. The server creates a random per-session value. It can arrive in server-rendered HTML, a same-origin response, or a response exposed to an exact trusted origin through CORS. The trusted form sends its hidden token and succeeds. Then the same browser becomes attacker.com: it can build equivalent HTML and receives the session cookie automatically, but it cannot read the protected token. Its mutation therefore fails. Logout or session expiry invalidates the token with the session. Prefer the framework's built-in implementation. XSS or a CORS leak can defeat the token's read-protection assumption. Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html

Start with the authentication mechanism. Without browser-attached credentials, classic CSRF does not apply. With cookie authentication, ask whether the endpoint accepts a simple request. This roughly means a GET, HEAD, or POST using a form-compatible content type rather than JSON. If it does, use a CSRF token. If every mutation requires preflight, an exact credentialed CORS allowlist can be the CSRF defense. A broad or reflected allowlist cannot. Origin checks, SameSite cookies, and Sec-Fetch-Site remain useful layers. Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html

Why does an application-only header help?

It forces a cross-origin script through CORS preflight

Server rule Reject every mutation without X-Banana-App: 1
HTML form Cannot set X-Banana-App → Rejected by the API
Cross-origin fetch X-Banana-App: 1 →
OPTIONSOrigin not allowed
✕ Real request never sent

The header is not secret. Requiring it makes CORS run before the mutation.

This defense is a consequence of CORS rules. A form cannot attach arbitrary request headers. JavaScript can request X-Banana-App, but because it is not CORS-safelisted, the browser first sends OPTIONS. With an exact origin allowlist, campaigns.banana.com fails that preflight and the actual mutation is never sent. The server must reject every mutation missing the header, or the attacker can fall back to a form-shaped request. The header is not authentication. Curl, backend clients, an allowed hostile origin, or XSS can still send it. Sources: https://fetch.spec.whatwg.org/ and https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html

Can SameSite be enough?

Sometimes. Its boundary is the site, not the origin.

A narrow yes SameSite=Strict can be the primary defense when
  • GET never changes state
  • every sibling subdomain is trusted
  • older or embedded browsers are out of scope
  • the server still checks Origin as a fallback
Different origins campaigns.banana.com ≠ auth.banana.com
Same site banana.com = banana.com
The cookie may be sent. SameSite does not stop our attack.
SameSite can be a reasonable primary CSRF defense in a narrow modern deployment. Strict is the clearest case. You must trust every sibling subdomain, keep all GET handlers read-only, accept the browser coverage, and preferably verify Origin as a fallback. It does not work for this story. Campaigns and auth have different origins, but they share the banana.com site, so SameSite treats the request as same-site. Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html

When can CORS defend this API?

01Check Origin against exact trusted origins.
02Require JSON or an application-only header on mutations.
03Reject form, text, and state-changing GET alternatives.
04PATCH + JSON already causes a browser preflight.
05None of this mattered here. The code explicitly allowed campaigns.banana.com.
This is the recap. “Make every mutation preflight” is shorthand and slightly misleading. Same-origin requests never need CORS preflight. Accept only non-simple mutation shapes, such as JSON or a required custom header, and reject simple form or text alternatives. A cross-origin browser then has to preflight automatically. This demo already uses PATCH and JSON, so no client change is required. In the incident, the browser performed every step correctly. The server explicitly approved the hostile campaign origin.

Step 03 · SSRF

A valid URL is not an allowed URL.

The destination came from the request. The credentials came from the server.

change-metadata.ts TypeScript 
const { role, subSystem } = req.body;

const target = makeUrl(
  `https://${subSystem}`,
);

await serviceClient.patch(target, { role });
serviceClient automatically authenticates as support-service
The assumption

subSystem names one of our services.

makeUrl() proves that the string is a URL. It does not prove that the service is allowed.

Attacker-controlled destination 
auth.banana.com/api/users/{attackerId}

The hostname and path both survive validation.

Request sent by the backend 
PATCH https://auth.banana.com/api/users/{attackerId}
Authorization: Bearer <support-service>
{ role: "admin" }

The server lends the request network access and its own identity.

Fix: server-owned destinations 
const hosts = {
  crm: "https://crm.banana.com",
  billing: "https://billing.banana.com",
};

const baseUrl = hosts[subSystem];
if (!baseUrl) throw InvalidSubSystem;

The request chooses a small identifier. The server chooses the URL.

URL parsing is not authorization. The attacker controls the hostname and path, while the service client contributes network reachability and a trusted identity. The fix is a strict mapping from a small region identifier to server-owned destinations.

Each defense stands on its own. An identifier allowlist prevents the write. Safe rendering prevents code execution. A destination allowlist prevents the internal request. Operation-level authorization prevents the role change. Defense in depth turns a bug into a contained bug.

}

It was meant to admit first-party frontends. It also admits attacker-controlled pages.

The modern fetch uses JSON and PATCH, so the browser correctly preflights it. The auth service allows credentialed requests from any banana.com subdomain because several frontends use the API. A marketing contractor is legitimately allowed to publish campaign content, but cannot access the auth service. Once that contractor account or pipeline is compromised, the suffix-based CORS policy accidentally promotes limited publishing access into a trusted auth origin. The browser approves the preflight, includes Maya's same-site session cookie, and sends the mutation.

Choosing the defense

To CSRF token or not CSRF token?

A token proves the application constructed the request, not merely the browser.

What the token adds

Proof that is not ambient

Cookieattached automatically
X-CSRF-Tokensupplied by the application

A hostile origin can cause the first. It cannot supply the second.

Tokenless option 01

Verify the request origin

  • Exact-match trusted origins
  • Referer fallback
  • Reject missing or null
  • Check every unsafe method
Tokenless option 02

Make every mutation preflight

  • Exact credentialed CORS allowlist
  • Require JSON or a custom header
  • Reject simple request formats
  • No state-changing GET
Every cookie-authenticated mutation needs a CSRF defense. Not necessarily a token.
The token is one way to prove that the request was constructed by the application. Every cookie-authenticated state change needs some CSRF defense, but the defense does not have to be a token. Strict server-side Origin and Referer verification can be sufficient if it fails closed. An exact credentialed CORS allowlist can also be sufficient for an API when every accepted mutation requires preflight, for example through JSON or a required custom header, and the API rejects all simple request shapes. The broad banana.com suffix rule meets neither standard.

Supply-chain control

npm install is not a security strategy.

Automatically receiving a patch means automatically trusting a new release.

npm install

No committed lockfile

^3.2.0 → latest compatible version
3.2.2 skips the known vulnerability 3.2.3 installs the supply-chain attack
The fix · npm ci

Committed lockfile

package-lock.json → reviewed 3.2.2
Repeatable across developer and CI machines Explicit updates arrive as lockfile changes
Install reviewed versions. Audit them continuously.
With no lockfile, npm install resolves the range again. A later build may incidentally receive a patched release, but the same mechanism also accepts an unreviewed or compromised patch release. The fix is to commit the lockfile and use npm ci, so CI installs exactly what was reviewed. That solves uncontrolled dependency drift. It does not remove the need to maintain the frozen tree as new vulnerabilities are disclosed, which is the job of the separate auditing process on the next slide.

What had to go wrong?

Three assumptions. One exploit.

Prototype pollution only gains teeth when several ordinary choices line up.

01 req.body

Unshaped input

Arbitrary nested keys reach generic object plumbing.

JSON.parse() is not the vulnerability.
02 target[key]

Prototype-aware write

A deep merge or path setter follows inherited properties.

This is the pollution source.
03 user.isAdmin

Security-sensitive read

Authorization accepts an inherited value as explicit data.

This is the gadget.
Impact amplifier A long-lived shared process lets one write affect unrelated requests. Break any required link and this exploit stops.
Count the first item as an architectural assumption rather than a vulnerability by itself. The two essential bugs are the unsafe write and a useful inherited read. In application code, though, all three gates normally need to line up: attacker-controlled keys must reach the source, the source must mutate a relevant prototype, and a gadget must consume the polluted property. Shared process state increases the blast radius but is not required for an exploit against the polluted target itself.

A fixed-shape DTO is the easy case. z.strictObject rejects unknown keys and returns parsed output. Recent Zod 4 versions safely keep __proto__ out of that output; version 4.4.3 briefly failed to report that particular key as an error even though it was dropped, and the reporting fix was subsequently merged. This defense only works if later code uses the parsed output. Prototype pollution deserves attention when attacker-controlled keys or paths meet dynamic, usually deep, object writes. Without attacker-controlled keys or paths, this data-only attack has no entry point. Schemas designed to preserve arbitrary keys, such as loose objects, records, or catchalls, need explicit key handling and an up-to-date Zod version. For genuine dictionaries, prefer Map or a null-prototype object. On sensitive reads, Object.hasOwn prevents inherited values from becoming authority. Node's --disable-proto flag removes or traps the legacy __proto__ accessor. A normal object's constructor still resolves to Object, so constructor.prototype reaches the same shared prototype. Treat the flag as hardening rather than the primary fix.

Defense in depth

Fix the source too.

The merge helper should remain safe when a caller forgets validation.

deep-merge.ts TypeScript 
const blocked = new Set([
  "__proto__", "constructor", "prototype",
]);

function deepMerge(target, source) {
  for (const [key, value] of Object.entries(source)) {
    if (blocked.has(key)) throw new Error("unsafe key");

    if (!isPlainObject(value)) {
      target[key] = value;
      continue;
    }

    const current = Object.hasOwn(target, key) &&
      isPlainObject(target[key]) ? target[key] : {};

    target[key] = deepMerge(current, value);
  }
  return target;
}
01 · Stop traversal

Block prototype-control keys

Reject them at every depth. Throwing also makes the attempted input visible.

02 · Ignore inheritance

Recurse into own values only

Never use an inherited object as the next merge target.

03 · Keep the contract narrow

Merge plain objects only

Replace arrays and special objects instead of recursively interpreting them.

Validate at the endpoint. Defend inside the helper. Keep both.
The critical repair is inside the reusable helper. Reject __proto__, constructor, and prototype at every recursion level. Object.hasOwn then prevents some other inherited property from becoming the recursive target. Restrict recursion to plain objects so arrays, dates, class instances, and other special values do not gain accidental merge behavior. Throwing is preferable to silently skipping a reserved key because callers can log or reject the request. This slide is the algorithm's security contract, not a recommendation to maintain a home-grown merge library. In production, use a current, tested library and keep the endpoint schema as the independent first defense.
